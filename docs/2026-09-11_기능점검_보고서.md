## 한눈에

앱을 실제로 띄워 화면 20개를 두 가지 너비로 모두 돌았고, API 45개에 권한·검증 29건을 직접 찔렀으며,
계획서와 구현을 한 줄씩 대조했다. **골격은 튼튼하다.** 가족 간 데이터 격리는 13건 모두 막혔고,
빈 상태 안내·상대 단위 글꼴·320px 대응 같은 고령자 기준이 문서가 아니라 코드에 들어가 있다.

문제는 **예외 경로와 파생 화면에서 그 기준이 새어 나간다**는 점이다. 아래 일곱 가지는 출시 전에
막아야 한다. 전부 재현했거나 코드에서 근거를 확인했다.

## 1. 출시 전에 막아야 할 것

### 1-1. 오전 9시 이전 기록이 전날로 저장된다

가장 시급하다. 부모님이 아침에 하는 모든 기록이 하루 전 날짜로 들어간다.

체크 화면 세 곳이 `new Date().toISOString().slice(0, 10)` 으로 날짜를 만든다. 이 값은 **세계 표준시**
기준이라 한국 시간 자정부터 오전 9시까지는 전날이 나온다.

| 파일 | 줄 |
|---|---|
| `webapp/src/pages/MealCheck.tsx` | 27 |
| `webapp/src/pages/MoodCheck.tsx` | 31 |
| `webapp/src/pages/SeniorHome.tsx` | 18 |

같은 저장소에 **이 함정을 피하려고 만든 함수가 이미 있다.** `shared/tabs.tsx` 의 `localDate()` 이고
주석에 "자정 근처에 UTC 로 밀리지 않게 로컬로 만든다" 라고 적혀 있다. 리포트와 건강기록 화면은 이걸
쓰는데, 정작 부모님이 입력하는 세 화면만 안 쓴다. 서버도 읽는 쪽은 한국 시간 기준이다.

**재현했다.** 브라우저 시계를 한국 시간 9월 12일 오전 8시로 맞추고 아침 식사를 눌렀더니:

```
앱이 서버로 보낸 값: {"check_date":"2026-09-11","slot":"breakfast","status":"ate"}
한국 날짜  : 2026-09-12
저장된 날짜: 2026-09-11
```

부모님이 겪는 것은 이렇다. 아침 7시 반에 식사 체크를 열면 **어제 답변이 오늘 것처럼 켜져 있다.**
"다 했네" 하고 닫으면 오늘 기록은 0건이다. 다시 누르면 어제 기록을 덮어쓴다. 옆 탭인 건강기록은
같은 아침을 "아직" 이라고 표시한다. 화면끼리 서로 다른 말을 한다.

고치는 법은 세 줄을 `localDate()` 로 바꾸는 것뿐이다. 함수는 이미 있다.

### 1-2. 30분 뒤 앱이 멈춘다

접속 토큰 수명이 30분인데, 만료를 감지해 갱신하는 코드가 **첫 화면에만** 있다. `shared/api.ts` 의
요청 함수는 401 을 받아도 아무것도 하지 않고, 화면 보호 장치는 토큰이 저장돼 있는지만 보고 만료는
보지 않는다.

**재현했다.** 갱신 토큰은 멀쩡하고 접속 토큰만 만료된 상태, 즉 앱을 30분 넘게 켜 둔 뒤 다시 보는
상황을 만들었다.

```
앱 안에서 약 화면을 바로 열면 → "오늘 드실 약을 불러오지 못했습니다"  토큰 갱신 안 됨
앱을 껐다 켜서 첫 화면을 거치면 → 토큰 갱신 됨, 정상 동작
```

부모님이 겪는 것은 이렇다. 아침에 앱을 켜 두고 점심에 앱 스위처로 다시 올린다. 첫 화면을 거치지
않으므로 갱신이 안 된다. 식사를 기록하려 하면 "불러오지 못했습니다" 가 뜬다. 빠져나갈 길은 앱을
완전히 종료하고 다시 켜는 것인데, 이 연령대에 기대하기 어려운 조작이다.

앱이 다시 앞으로 올 때 부르는 코드는 있지만 심장박동 신호만 보내고 토큰 갱신은 하지 않는다.

### 1-3. 오류 화면의 유일한 버튼이 강제 로그아웃이다

`webapp/src/pages/SeniorHome.tsx:61-68`

```jsx
if (error) {
  return (
    <Screen title="홈">
      <Notice tone="error">{error}</Notice>
      <BigButton onClick={signOut}>처음으로</BigButton>   {/* 토큰을 지운다 */}
    </Screen>
  );
}
```

지하철이나 엘리베이터에서 통신이 한 번 끊기면 홈 전체가 이 화면이 된다. 화면에 있는 유일한 버튼이
"처음으로" 인데 실제 동작은 **완전 로그아웃**이다. 부모님은 "홈으로 돌아가기" 로 읽고 누른다.

부모님은 비밀번호가 없다. 다시 들어오려면 자녀 이름과 자녀 전화번호를 정확히 입력해야 한다.
자녀가 옆에 없으면 **혼자 힘으로 복구할 수 없다.** 다시 시도 버튼도 없다.

같은 자리에 로그아웃 버튼 자체도 확인 없이 즉시 동작한다. 화면에서 가장 큰 버튼이고, 바로 아래
회원 탈퇴는 두 단계로 확인을 받는다. 되돌리기 난이도가 비슷한 두 동작인데 보호 수준이 정반대다.

### 1-4. 스크롤하면 제목이 버튼을 덮는다

`webapp/src/shared/redesign.css:88` 이 화면 머리글 배경을 투명으로 덮어쓴다. 머리글은 위에 고정돼
있으므로, 스크롤한 본문이 제목 뒤로 그대로 비친다.

```css
.screen-head { background: transparent; }   /* tokens.css 의 불투명 배경을 덮는다 */
```

네 화면에서 확인했고 모두 배경이 완전 투명이었다. 부모님 약 화면이 가장 나쁘다. 제목 "약 복용" 이
"먹었어요 / 안 먹었어요" 버튼 위에 겹쳐 찍힌다. 부모님 화면의 주된 동작 버튼이다.

탭바에서 같은 문제를 겪고 `background: #fff` 로 고친 기록이 있는데, 머리글은 빠졌다.

### 1-5. 매일 아침 9시에 이상 징후 오탐이 나간다

`backend/app/services/alert_engine.py:81` 의 `today = now.date()` 에서 `now` 가 세계 표준시다.
판정 조건은 "오늘 체크 0건 + 활동 신호 0건" 이고, 스캔은 15분마다 돈다.

여기에 활동 신호는 **절대 수집되지 않는다.** `bridge.ts` 의 수집 함수가 빈 배열만 돌려주는 미구현
상태라 신호 수는 항상 0이다.

1-1 과 겹쳐서 최악이 된다. 한국 시간 오전 8시에 아침 식사를 체크하면 전날 날짜로 저장된다. 오전
9시에 세계 표준시 날짜가 넘어가면 판정 기준일이 바뀌는데, 그 날짜의 체크는 0건이다. 결과적으로
**아침을 성실히 기록한 부모님이 9시에 "오늘 아직 아무 기록이 없어요" 이상 징후 알림을 받는다.**
그 알림은 자녀 전원에게 높은 중요도로 푸시된다.

계획서가 최대 위험으로 꼽은 "이상 징후 오탐 → 자녀 신뢰 하락" 이 매일 아침 구조적으로 일어난다.

### 1-6. 앱에서 식사 사진이 항상 깨진다

사진 표시가 세 곳에서 상대 경로를 쓴다.

```jsx
<img className="thumb" src={`/uploads/${photo_path}`} />
```

API 요청은 절대 주소를 붙이는데 이미지만 안 붙인다. 앱의 오리진은 `https://localhost` 라서
이 경로는 서버가 아니라 **앱 번들 안**을 가리킨다. 운영 서버에서 사진을 내주는 것은 아파치인데
거기까지 닿지 않는다.

업로드 자체는 절대 주소를 쓰므로 성공하고 "사진을 올렸어요" 도 뜬다. 그런데 썸네일 자리에는 깨진
이미지가 나온다. 브라우저에서 열 때만 정상이다. 실기기에서 확인이 필요하다.

### 1-7. 비밀번호 찾기가 없다

`GuardianLogin.tsx` 에 재설정 링크가 없고 서버에도 관련 엔드포인트가 없다. 검색해서 확인했다.

자녀 계정이 이 서비스의 유일한 뿌리다. 부모님은 자녀 이름과 번호로 들어오고, 마지막 자녀가
탈퇴하면 가족째 파기된다. 자녀가 비밀번호를 잊으면 **자녀도 부모님도 들어갈 방법이 없다.**

이메일은 이미 필수로 받고 있고 메일 설정도 있으므로 기술적 장애물은 없다.

덧붙여 폼 다섯 개 전부 `<form>` 태그가 아니고 자동 완성 힌트가 하나도 없다. 키보드의 완료 키가
동작하지 않고, 비밀번호 관리자가 저장을 제안하지도 않는다. 잊어버릴 확률을 스스로 높이고 있다.

## 2. 기획자 관점 — 계획서와 현실의 차이

### 계획에 있는데 없는 것

**형제가 같은 가족에 들어올 방법이 없다.** 계획서 1.2 는 "형제도 같은 가족에 들어올 수 있다" 고
적었는데, 회원가입은 **항상 새 가족을 만든다.** 기존 가족에 합류하는 경로가 없다. 1.4 에서
초대코드를 없애면서 대체 수단을 만들지 않았고, 두 조항이 서로 모순인 채 남아 있다.

둘째 자녀가 같은 부모님을 등록하면 "이미 다른 가족에 등록된 번호입니다" 로 막히고, 어떻게 하라는
안내가 없다. 탈퇴 로직은 "다른 자녀가 있으면" 분기를 정성껏 만들어 뒀는데 **그 상태에 도달할 방법이
없다.**

**알림 꺼짐 배너가 없다.** 계획서 8.5.8 과 위험 대응표에 두 번 명시된 항목이다. 부모님이 알림 권한을
거부하면 복약 알림이 아예 안 울리는데, 부모님 화면에도 자녀 화면에도 그 사실이 표시되지 않는다.
권한 상태를 서버에 올리지도 않아 자녀가 알 방법이 없다.

여기에 더 나쁜 것이 겹친다. 알림을 거부하면 단말 등록이 안 되고, 단말 행이 없으면 "장시간 미응답"
판정이 통째로 건너뛰어진다. **알림을 거부한 부모님은 이상 징후 감지 대상에서 빠지고, 아무도 그 사실을
모른다.**

**메일 리포트가 한 통도 안 나간다.** 가입 화면에서 "부모님 리포트도 이 주소로 보내드립니다" 라고
안내하고 동의까지 받는데, 메일 발송 모듈은 어디에서도 호출되지 않는다. 약속하고 받은 동의를 지키지
않는 상태다.

**생활 패턴 수집이 없다.** 서버 수신부와 집계, 화면까지 다 있는데 보내는 쪽만 미구현이다. 계획서
13장에서 M5 로 잡은 것이라 연기 자체는 정당하지만, MVP 기능 목록에는 들어 있다. 그 결과 활동량은
항상 "기록 없음" 이고 리포트의 시간대별 그래프는 늘 비어 있다.

**파기 정책을 실행하는 작업이 없다.** 공개된 방침에 알림 이력 90일, 활동 신호 90일이라고 못 박아
뒀는데 삭제하는 주기 작업이 없다. 무한히 쌓인다.

### 만들어졌는데 기획과 다른 것

**어르신 동의를 코드가 대신 눌러 준다.** 부모님이 목록에서 자기 이름을 한 번 누르면 서버가 조용히
동의 시각을 찍고 동의 이력을 남긴다. 부모님은 동의 문구를 한 글자도 보지 않는다. 그런데 공개된
개인정보처리방침에는 "별도의 명시적 동의를 받은 뒤에만 수집합니다" 라고 적혀 있다. 건강 정보는
민감정보다. 방침과 코드가 다르다.

**동의 체크박스에 읽을 문서가 없다.** 가입 화면에 개인정보처리방침 링크도 이용약관도 없다.
방침 페이지는 앱 번들에 들어 있는데 **앱 어느 화면에서도 열 수 없다.** 이용약관은 아예 없다.

**토큰을 브라우저 저장소에 둔다.** 계획서 11장이 "앱에서는 보안 저장소를 쓰고 `localStorage` 금지"
라고 명시했는데 지켜지지 않았다. 갱신 토큰 수명이 180일이라, 웹뷰 저장소에 반년짜리 건강정보 접근
자격이 평문으로 남는다.

**복약 재알림이 꺼져 있다.** MVP 기능 목록의 "미체크 시 단계별 재알림" 이 지금 0회다. 9월 9일
결정으로 보류한 것이고 문서화도 돼 있지만, 기능 목록은 갱신되지 않았다. 로컬 알람을 뺀 이상
재알림의 중요도가 올라갔다. 통신이 끊기면 한 번도 안 울리는데 재알림도 없으면 이중 실패다.

**2시간 미복용 시 자녀에게 푸시한다.** 계획서는 이 시점에 "자녀에게는 푸시하지 않음" 이라고 명시했다.
지금은 보류 플래그 때문에 실행되지 않지만, 켜는 순간 발현된다.

### 여정의 구멍

**자녀가 이상 징후를 받고 할 수 있는 일이 읽음 표시뿐이다.** 알림 카드의 버튼 이름은 "상세 확인"
인데 실제로는 확인 처리만 하고 카드가 목록에서 사라진다. 상세 화면이 없다. 자녀 화면 어디에도
부모님에게 **전화 거는 버튼이 없다.** "24시간 동안 응답이 없어요" 를 보고 자녀가 앱 안에서 할 수
있는 행동이 없다.

**탭을 누르면 탭바가 사라진다.** 부모님 탭 네 개 중 "일정", 자녀 탭 네 개 중 "메시지" 가 탭바 없는
화면으로 간다. 돌아갈 길이 좌상단 작은 화살표뿐이다. 고령자 화면에서 탭이 있다가 없어지는 것은
방향 감각을 잃게 하는 대표적인 패턴이다.

참고로 자녀 탭의 "메시지" 는 알림 목록으로 간다. 메시지 기능은 없다. 있지도 않은 기능을 기대하게
만드는 이름이다.

**부모님을 "빼기" 하면 기록이 갈 곳 없이 남는다.** 가족 구성원 행만 지우므로, 그 부모님 계정은
아무 자녀도 볼 수 없고 본인도 다시 로그인할 수 없는데 기록은 영구히 남는다. 이미 발급된 갱신 토큰은
최대 180일 유효해서, 가족에서 뺀 부모님이 자기 앱에서 계속 기록할 수 있다.

## 3. 개발자 관점

### 3-0. 보안 — 확인된 구멍

#### 서명 키가 비어 있으면 누구나 토큰을 만든다

가장 위험하다. 설정 파일 한 줄에 달려 있다.

```python
SECRET_KEY: str = "dev-only-change-me"   # backend/app/core/config.py:17 — 공개 저장소에 적혀 있다
```
```
SECRET_KEY=                              # deploy/.env.example:14 — 빈 값인 채로 예시가 나간다
```

기동할 때 이 값을 검사하는 코드가 없다. 그리고 **빈 키로도 토큰이 서명되고 검증된다.** 직접 확인했다.

```
빈 키로 서명: eyJhbGciOiJIUzI1NiIsInR5cCI6 ...
빈 키로 검증: {'sub': 'x'}
```

공격 경로가 열려 있다. 부모님 조회 API 는 **인증 없이** 어르신의 고유 번호를 돌려준다. 내 점검에서
확인한 응답이다.

```
POST /auth/senior/lookup  →  200
{"family_name":"보호자A님의 가족","seniors":[{"id":"f19fef52-...","name":"어르신A"}]}
```

그 고유 번호로 토큰을 빈 키나 저장소에 적힌 기본 키로 서명하면 그 어르신의 건강정보 전부에 접근한다.
비밀번호도 전화번호도 필요 없다.

**서버의 `.env` 에 실제 키가 들어 있는지 지금 확인해야 한다.** 예시 파일을 그대로 복사했다면 비어 있다.
막는 법은 운영 환경에서 키가 비었거나 기본값이면 기동을 거부하게 하는 것이다.

#### HTTP 가 리다이렉트 없이 그대로 응답한다

저장소의 아파치 설정은 HTTPS 블록이 통째로 주석 처리돼 있다. 다만 **실제 서버는 다르다.** 직접 확인했다.

```
https://hubfamily.co.kr  →  200 OK,  Strict-Transport-Security: max-age=31536000
http://hubfamily.co.kr   →  200 OK   ← 리다이렉트 없이 평문으로 응답한다
```

HTTPS 는 정상이고 HSTS 도 붙어 있다. 문제는 평문 HTTP 도 그대로 내용을 준다는 것이다. HSTS 헤더는
HTTPS 응답에서만 효력이 있어서, 처음 오는 사람이 HTTP 로 들어오면 평문으로 오간다. 앱은 절대 주소로
HTTPS 를 쓰므로 영향이 없고, 웹으로 접속하는 경우에 해당한다.

저장소 설정 파일이 운영 서버와 어긋나 있는 것도 같이 정리할 일이다.

#### 가족에서 뺀 부모님 번호를 남이 등록하면 과거 기록까지 가져간다

부모님을 가족에서 "빼기" 하면 소속 행만 지우고 계정과 기록은 남는다. 그런데 부모님 등록은 전화번호로
기존 계정을 찾고, **소속이 없으면 조건 없이 자기 가족으로 편입한다.** 소속 확인만 있고 본인 확인이 없다.

점검에서 재현됐다. 무관한 사람이 가입해 그 번호를 등록하자 새 계정이 아니라 원래 계정이 그대로
딸려 왔고, 과거 식사 기록과 리포트를 읽을 수 있었다. 제출한 이름은 무시되고 원래 이름이 돌아오므로
**전화번호 하나만 알면 된다.** 동의 시각이 이미 차 있어 재동의도 받지 않는다.

빼기 할 때 기록도 함께 파기하거나, 재편입 때 본인 확인을 다시 받아야 한다.

#### 로그인 시도에 제한이 없다

부모님 로그인은 자녀 이름과 전화번호만으로 토큰이 나온다. 설계상 한계로 문서에 적혀 있는데,
**완화 장치가 하나도 없다.** 속도 제한 미들웨어도, 시도 횟수 기록도 코드에 없다.

조회 API 가 인증 없이 가족 이름, 자녀 이름, 부모님 실명 목록, 고유 번호를 준다. 자녀 이름을 아는
지인이라면 번호 여덟 자리만 남는다. 자녀 비밀번호 로그인도 마찬가지로 무제한이다.

Redis 컨테이너는 이미 떠 있는데 **코드 어디에서도 쓰이지 않는다.** 시도 횟수를 둘 자리가 준비돼 있다.

#### 식사 사진이 인증 없이 공개된다

아파치가 업로드 폴더를 `Require all granted` 로 그대로 내준다. 경로에 난수가 들어가 추측은 어렵지만
"주소를 아는 사람이 권한자" 모델이다. 그 주소는 접근 로그에 남고, 이 서버는 사이트 100여 개가 함께
도는 공용 호스트다. 식사 사진에는 집 안 풍경과 약봉지가 찍힌다.

#### 푸시 토큰만 알면 남의 단말을 가로챈다

단말 등록이 토큰으로만 기존 행을 찾고 소유자를 확인하지 않는다.

```python
device = await session.scalar(select(Device).where(Device.push_token == payload.push_token))
...
device.user_id = user.id     # 남의 행을 내 것으로 바꾼다
```

결과는 조용하다. **피해자는 복약 알림을 더 이상 받지 못하고**, 알림이 이 제품의 존재 이유다.

#### 감사 로그의 IP 를 위조할 수 있다

전달 헤더의 **맨 앞** 값을 클라이언트 IP 로 쓴다. 아파치는 실제 IP 를 뒤에 덧붙이므로, 클라이언트가
헤더를 넣어 보내면 그 값이 채택된다. 이 기록은 개인정보보호법 대응용 조회 이력이다. 프록시가 한 단이니
뒤에서 두 번째를 취해야 한다.

### 권한과 격리 — 통과

가족 두 개를 만들어 A 의 토큰으로 B 의 자원을 29가지 방법으로 건드려 봤다. **남의 가족 데이터에
접근하는 경로는 13건 모두 막혔다.**

```
A자녀 → B의 약 수정/삭제            403 NOT_SAME_FAMILY
A자녀 → B의 일정 수정/삭제/알림발송   403 NOT_SAME_FAMILY
A자녀 → B어르신 리포트/활동/약목록    403 NOT_SAME_FAMILY
A자녀 → B어르신 빼기/수정            404 SENIOR_NOT_FOUND
A자녀 → B어르신에 약·일정 등록        403 NOT_SAME_FAMILY
A어르신 → B의 약 복용기록            403 SENIOR_ONLY
```

역할 분리도 자녀 전용 동작 세 가지가 모두 막혔다. 토큰 검증과 입력 검증도 대체로 견고했다.
빈 이름, 잘못된 시각 형식, 500자 이름, 잘못된 값 모두 422 로 거부됐다.

### 구멍 세 가지

**부모님 전용 가드가 정의만 되고 쓰이지 않는다.** `core/deps.py` 에 `require_senior` 가 있는데
**어느 엔드포인트도 쓰지 않는다.** 그 결과 자녀 토큰으로 식사 체크와 기분 체크가 200 으로 통과한다.
자기 자신의 기록으로 저장되므로 남의 데이터를 건드리는 것은 아니지만, 쓰이지 않을 데이터가 생기고
역할 경계가 일관되지 않다.

```
자녀 → 식사 체크(어르신 전용)   200   (403 이어야 함)
자녀 → 기분 체크(어르신 전용)   200   (403 이어야 함)
```

**미래 날짜 기록을 받는다.** `check_date` 에 상한이 없어서 2099년 1월 1일로 식사 체크가 저장된다.

**같은 가족의 부모님끼리 서로의 기록을 볼 수 있다.** 가족 접근 검사가 역할을 보지 않고 가족이
겹치면 통과시킨다. 방침에는 "보호자에게만 표시됩니다" 라고 적혀 있다. 부부가 둘 다 등록된 경우에
해당한다. 현재 화면은 이 요청을 만들지 않지만 API 는 열려 있다.

### 알림이 안 가거나 두 번 가는 경우

#### 일정 시각을 바꾸면 그 알림이 영영 안 간다

중복 방지 키에 **시각이 들어 있지 않다.**

```python
dedupe_key=f"schedule:{sch.id}:{minutes}"                          # 일정 — 시각 없음
dedupe_key=f"med:{med.id}:{occ.scheduled_at.isoformat()}:L{due}"   # 복약 — 시각 있음
```

한 번 보내면 그 키가 이력에 남고, 이후 같은 키는 기간 제한 없이 건너뛴다. 그래서 **자녀가 병원
예약을 미루면 부모님은 바뀐 시각에 알림을 받지 못한다.** 조용히 사라진다.

복약 쪽은 예정 시각이 키에 들어 있어 안전하고, 어제 그걸 확인하는 테스트까지 넣었다. 일정만 같은
처리를 안 했고 테스트도 없다. 키에 시작 시각을 넣으면 해결된다.

#### 푸시가 실패해도 "보냈다"로 기록하고 다시 시도하지 않는다

발송 함수는 실패해도 예외를 올리지 않고 실패 이력을 남긴 뒤 정상 반환한다. 부르는 쪽은 그 결과를
보지 않고 단계를 올린다. 그래서 단말 미등록, 파이어베이스 일시 장애, 애플 일시 장애 모두
**약 알림이 영구히 유실된다.** 나중에 다시 시도하지 않는다.

#### 워커가 멈췄다 돌아오면 그 시각 알림이 통째로 사라진다

재알림이 꺼져 있는 지금, 워커가 30분 이상 멈췄다 돌아오면 그 사이 예정이던 복약 건은 단계 판정에서
걸러져 건너뛰어진다. 일정 알림은 창이 1분이라 더 짧게 밀려도 유실된다.

배포 스크립트가 워커를 재빌드하므로 **배포할 때마다 몇 분간 정지한다.** 아침 8시 근처에 배포하면
그날 약 알림이 안 간다.

#### 같은 체크가 동시에 오면 500 이 난다

체크 세 종류가 "조회해 보고 없으면 삽입" 패턴인데 잠금도 충돌 처리도 없다. 파일 첫머리 주석이
**"오프라인 큐로 같은 요청이 여러 번 올 수 있다"** 고 정확히 예고해 둔 상황이다. 유니크 제약에
걸리면 예외 핸들러가 없어 500 으로 샌다. 부모님 화면에는 "연결이 원활하지 않습니다" 가 뜨고 큐는
다시 보낸다.

웹앱은 중복 방지 헤더를 보내고 있다. **서버는 그 헤더를 어디서도 읽지 않는다.**

#### 약 정보를 고치면 과거 리포트가 소급해서 바뀐다

리포트는 **현재** 약 규칙을 과거 날짜에 펼쳐서 기록과 맞춘다. 그래서 복용 시각을 바꾸면 지난주에
실제로 체크한 기록이 어디에도 매칭되지 않아 과거 리포트가 "0회 복용" 으로 바뀐다. 약을 내리면
과거 복약 기록이 리포트에서 통째로 사라진다. 건강기록은 그 시점의 사실로 고정되어야 한다.

#### 동기 호출이 서버 전체를 멈춘다

파이어베이스 발송이 완전히 동기 함수인데 비동기 함수 안에서 그대로 호출된다. 서버는 프로세스 하나로
뜬다. 그래서 자녀가 일정 알림 전송을 누르는 동안 **그 서버의 모든 요청이 멈춘다.** 파이어베이스가
느리면 그 시간만큼 API 전체가 응답하지 않는다.

### 오류 문구가 사용자에게 잘못 전달된다

입력 검증 오류가 공통 규약을 따르지 않는다. 예외 처리기가 두 종류만 등록돼 있어서, 검증 오류는
기본 형식으로 나가고 웹앱은 그걸 해석하지 못한다.

결과적으로 **모든 입력 오류가 "연결이 원활하지 않습니다" 로 보인다.** 비밀번호가 짧아도, 시각 형식이
틀려도 네트워크 문제라고 안내한다. 서버에는 친절한 한국어 메시지가 준비돼 있는데 전달되지 않는다.

덧붙여 검증 오류 응답이 **제출한 비밀번호 원문을 그대로 돌려준다.** 보낸 본인에게 가는 것이라 유출
강도는 낮지만, 오류 수집 도구가 응답 본문을 저장하면 비밀번호가 남는다.

숫자 입력에 범위 제한도 없다. 글자 배율에 `99999999999` 나 음수가 들어가고, 걸음 수에 음수가 들어간다.
지금 테스트는 SQLite 라 통과하지만 **운영 PostgreSQL 에서는 정수 범위를 넘겨 500 이 난다.**

전화번호는 형식 검증이 없어 `----------` 로 가입하면 빈 문자열이 저장된다. 더 실질적인 문제는 정규화
규칙이 하나뿐이라, 자녀가 `010-1111-2222` 로 가입하고 부모님이 `+82 10-1111-2222` 를 입력하면 서로
다른 값이 되어 로그인이 안 된다는 것이다. 부모님은 원인을 알 수 없고, 이 화면은 곧 이탈이다.

### 테스트가 못 보는 곳

자동 테스트 66개는 도메인 규칙을 잘 고정하고 있다. 다만 구조적으로 못 보는 영역이 있다.

**테스트가 SQLite 라 운영 제약이 하나도 검증되지 않는다.** 특히 외래키다. 탈퇴 서비스 첫머리에
*"외래키에 삭제 연쇄가 없다. 지우는 순서가 곧 제약 조건이다"* 라고 적어 뒀는데, **SQLite 는 기본적으로
외래키를 강제하지 않아 순서를 틀려도 테스트가 통과한다.** 안전망이라 믿는 것이 작동하지 않는다.
설정 한 줄로 켤 수 있다.

**고아 행 검사 테스트가 사실상 빈 테이블을 센다.** 내가 어제 넣은 것이다. 준비 단계에서 만드는
데이터가 다섯 종류뿐이라 알림, 감사 로그, 활동 신호 같은 나머지 테이블은 한 행도 없이 검사된다.
빈 테이블은 당연히 0이다. **탈퇴 서비스에서 비상 연락처를 지우는 줄을 삭제해도 이 테스트는 통과한다.**
게다가 검증하는 경로가 "가족 전체 삭제" 하나뿐인데, 고아 행이 생길 수 있는 쪽은 부분 삭제다.

**워커에 테스트가 하나도 없다.** 일정 알림 로직이 워커 파일 안에만 있어서, 위의 일정 중복키 버그가
테스트를 받지 못했다.

**시간대 테스트가 실행 시각에 의존한다.** 한국 시간 오전 9시 이후에 돌리면 날짜 버그가 드러나지
않는다. 시각을 고정할 수 있어야 한다.

### 앱 코드에서 나온 것

**부모님을 빠르게 전환하면 다른 부모님의 데이터가 표시될 수 있다.** 요청 취소나 무효화 장치가
없어서, 어머니 요청이 비행 중일 때 아버지를 고르면 늦게 도착한 어머니 응답이 화면을 덮어쓴다.
화면 상단에는 아버지 이름이, 숫자는 어머니 것이 뜬다. 건강 데이터에서 사람이 뒤바뀌는 표시다.
같은 구조가 일곱 화면에 있다.

**한 번 난 오류가 사라지지 않는다.** 재시도 전에 오류 상태를 비우는 코드가 없다. 날짜를 넘기다
한 번 실패하면, 이후 정상 데이터가 로드돼도 빨간 오류 배너가 그대로 남는다. 더 나쁜 것은 오류가
한 번 나면 로딩 표시 조건이 막혀서 **이후 모든 로딩에서 화면이 빈 채로 굳는다.**

**부분 실패가 화면 전체를 지운다.** 리포트 화면은 네 가지를 한꺼번에 불러오고 하나라도 실패하면
전부 감춘다. 그중 활동 신호는 아직 미구현 기능이다.

**실패한 기록이 성공처럼 보인다.** 오프라인 큐가 모든 예외를 오프라인으로 간주해 큐에 넣고, 화면은
낙관적으로 성공 표시를 한다. 401 같은 영구 실패도 큐에 들어가 재시도 상한 없이 영원히 쌓인다.
"아직 전송 안 됨" 표시가 어디에도 없다. 이 상태를 보여줄 함수가 만들어져 있는데 아무 데서도 안 쓴다.

**홈 화면이 실패를 0점으로 위장한다.** 체크 조회가 실패하면 오류를 숨기고 0/6 을 진짜 값인 척
넣는다. 다 기록한 부모님이 0점과 "오늘을 시작해 볼까요?" 를 본다.

**요청에 타임아웃이 없다.** 응답이 안 오는 상황에서 몇 분간 매달리고, 그동안 화면은 움직이지 않는
회색 문장 하나로 고정된다. 오류도 안 뜨고 재시도 버튼도 없다.

**중복 발송 방지가 없다.** 일정 알림 전송 버튼에 잠금이 없어서, 반응이 느리면 자녀가 한 번 더
누르고 부모님 폰에 같은 알림이 두 번 울린다. 복약 알림을 알람 채널로 강하게 다루는 앱이라 체감
비용이 크다.

### 타입과 죽은 코드

타입은 건강하다. `any` 0개, 타입 무시 지시문 0개, 타입 검사 통과. 위험한 단언 세 곳은 모두 방어
가능한 수준이다.

죽은 코드는 열두 건 있다. 안 쓰는 컴포넌트 다섯, 안 쓰는 함수 넷, 안 쓰는 아이콘 열네 개, 그리고
**아무것도 억제하지 않는 린트 무시 주석 여섯 개**다. 그 주석들이 억눌렀다고 표시한 의존성 누락이
바로 위의 경쟁 상태와 오류 잔존의 원인이다.

CSS 두 파일이 175개 선택자에서 충돌한다. 나중에 불리는 쪽이 이기므로 `tokens.css` 3,389줄 중
상당 부분은 실행되지 않는다. 실제 사고도 있었다. 세그먼트 탭 높이가 44px 로 정의돼 있는데 다른
파일이 40px 로 낮춘다. 접근성 기준을 낮추는 덮어쓰기가 조용히 일어난다.

## 4. 사용자 관점

### 잘 되어 있는 것부터

실제로 돌려 보니 기본기가 탄탄했다.

- 화면 20개를 390px 과 320px 에서 모두 열었는데 **JS 오류 0건, 가로 스크롤 0건**
- 빈 상태 안내가 다 있다. 부모님 0명, 약 0개, 알림 0건 모두 "먼저 부모님을 등록해 주세요" 같은
  다음 행동을 알려준다
- 통신이 끊긴 상태에서도 세 화면 모두 안내 문구가 나온다
- 기분 버튼을 세 번 연타해도 전송은 한 번만 간다
- 글자 크기가 **전부 상대 단위**라 기기 설정을 따른다. 고정 px 글꼴이 한 곳도 없다
- 약을 체크하면 "복용 완료" 배지가 글자로 뜨고 두 버튼이 남아 바로 정정할 수 있다. 색만으로
  구분하지 않는다

핵심 흐름도 정상이었다. 부모님이 식사·약·기분을 체크하면 자녀 홈에 "식사 1/3, 약 복용 1/1 완료,
기분 좋음" 으로 즉시 반영되고, 자녀가 추가한 약이 부모님 화면에 바로 나타난다. 로그아웃 후
뒤로가기로 돌아가지지도 않는다.

### 부모님이 겪는 문제

앞의 1-1 부터 1-4 까지가 모두 여기 해당한다. 그 외에:

**"앨범에서 고르기" 가 앱에서 가장 작은 버튼이다.** 식사 사진 아래 "찍기 대신 앨범에서 고르려면:
아침 점심 저녁" 에서 각 글자가 버튼인데 높이 32px, 너비 38px 이고 서로 붙어 있다. 점심을 누르려다
아침을 누르면 엉뚱한 끼니에 사진이 붙는다. 링크 이름이 "아침" 이라 무슨 동작인지도 알 수 없다.

**사진을 올리는 동안 아무 표시가 없다.** 진행 표시도 버튼 잠금도 없어서, 수 초 동안 화면이 무반응
이다. 안 눌린 줄 알고 다시 누르면 카메라가 또 열린다.

**"안 먹었어요" 를 골랐는지 알아보기 어렵다.** "먹었어요" 는 진한 초록으로 채워지는데 "안 먹었어요"
는 배경이 흰색에서 아주 연한 회색으로만 바뀐다. 백내장이나 노안이 있으면 구분이 어렵다.

**로딩 표시가 움직이지 않는 회색 문장 한 줄이다.** 이름은 스피너인데 애니메이션이 없다. 시력이
떨어지는 사용자에게는 "아무 일도 안 일어나고 있다" 로 읽힌다.

**기기 글자를 키우면 홈 타일 글자가 잘린다.** 글자는 상대 단위인데 타일 크기와 화면 분기는 고정
px 이라 같이 커지지 않는다. 넘치면 스크롤 없이 잘린다. 정작 더보기 화면에는 "글자가 작으면 휴대폰
설정의 글자 크기를 키워 주세요. 앱이 따라갑니다" 라고 안내한다. 그 말을 따르면 홈이 깨진다.
정확한 배율 임계값은 실기기 확인이 필요하다.

### 자녀가 겪는 문제

3장의 경쟁 상태, 오류 잔존, 중복 발송이 모두 여기 해당한다. 그 외에:

**"상세 확인" 을 눌러도 상세가 없다.** 누르면 그 카드가 목록에서 사라진다. 내용을 더 보려다
읽던 항목을 잃는다.

**"빼기" 가 파괴적인데 가장 흐리고 작다.** 글자색 대비가 2.50:1 로 기준 4.5:1 에 크게 못 미친다.
확인 창은 웹뷰 기본 경고창이라 앱 안에서 갑자기 브라우저 창이 뜬 것처럼 보인다. 부모님 계정과
기록에 정확히 무엇을 하는지도 알려주지 않는다. 탈퇴 화면은 그걸 제대로 보여주는데 여기는 아니다.

**일정 카드의 "수정" 과 "지우기" 가 4px 간격으로 붙어 있다.** 높이 40px 짜리 두 글자 버튼이고
그중 하나가 복구 불가능한 삭제다.

**약 알림 스위치가 색으로만 구분되고 높이가 30px 다.** 앱에서 가장 작은 대화형 요소다. 읽어주는
기능에는 정확히 연결돼 있어서 문제는 눈으로 보는 쪽이다.

### 터치 영역

계획서 기준은 56px 인데, 부모님이 직접 만지는 기본 버튼은 대체로 지켜졌고 파생 컨트롤에서 무너진다.

| 요소 | 크기 | 화면 | 누가 |
|---|---|---|---|
| 앨범에서 고르기 | 32px | 식사 체크 | 부모님 |
| 톱니(더보기) | 40×40px | 부모님 홈 | 부모님 |
| 기록하기 › | 40px | 건강기록 | 부모님 |
| 세그먼트 탭 | 40px | 일정·알림·약관리 | 양쪽 |

| 연필(수정) | 40×40px | 약 관리 | 자녀 |

### 색 대비

프로젝트가 스스로 정한 기준은 4.5:1 이다. 직접 계산해 확인했다.

| 토큰 | 실제 색 | 흰 카드 위 | 바탕 위 | 판정 |
|---|---|---|---|---|
| `--ink` | `#1c2b5c` | 13.55:1 | 12.77:1 | 통과 |
| `--ink-2` | `#4b587f` | 7.00:1 | 6.59:1 | 통과 |
| `--ink-3` | `#8a95b8` | 2.97:1 | 2.80:1 | **미달** |

본문과 안내 문구는 넉넉히 통과한다. 문제는 `--ink-3` 하나인데, 하필 **기능 버튼의 글자색**이다.
회원 탈퇴 링크, 빼기 버튼, 그리고 입력란의 예시 글자에 쓰인다. 이 앱은 예시를 정보로 쓴다
("김영희", "010-1234-5678"). 부모님이 읽어야 하는 내용인데 2.97:1 이면 옅게 흐려 보인다.

> 점검 중 한 번 틀렸다가 바로잡은 부분이다. `tokens.css` 의 값으로 계산하면 세 개 모두 미달로
> 나오는데, `redesign.css` 가 나중에 불려 색을 전부 덮어쓴다. 실제 적용되는 것은 위 표의 값이다.
> 같은 값이 두 파일에 다르게 있는 구조(3장 끝의 175개 충돌)가 이런 오판을 부른다.

### 어제 만든 탈퇴 화면의 결함

내가 어제 만든 화면에서 **정의되지 않은 CSS 변수 세 개**를 쓰고 있었다. `--text-md`, `--text-lg`,
`--ink-1` 은 어디에도 정의돼 있지 않다. 확인했다.

그 결과 되돌릴 수 없는 화면의 두 제목이 **본문과 똑같은 크기**로 렌더된다.

- "탈퇴하면 아래 기록이 모두 지워집니다"
- "정말 탈퇴하시겠어요?"

제목이 제목처럼 보이지 않아 경고의 무게가 사라진다. 한 줄짜리 수정이다.

캡처는 `docs/screenshots/audit/` 에 44장 있다. 이 폴더는 git 에 올리지 않는다.

점검 중 틀렸다가 확인 후 바로잡은 것이 넷 있다.

- 약 체크에 되돌리기가 없다고 봤으나, 두 버튼이 남아 바로 정정할 수 있었다.
- 일정 관리 빈 상태에 안내가 없다고 봤으나, 있었다.
- 색 대비가 세 토큰 모두 미달이라고 봤으나, 덮어쓰기 전 값으로 계산한 것이었다. 실제로는 하나만 미달이다.
- **HTTPS 가 꺼져 있다고 볼 뻔했다.** 저장소의 아파치 설정에는 HTTPS 블록이 주석 처리돼 있지만
  실제 서버는 HTTPS 로 정상 동작하고 HSTS 도 붙어 있다. 직접 요청해 확인했다. 실제 문제는
  평문 HTTP 가 리다이렉트 없이 응답한다는 쪽이다.

마지막 건은 저장소 설정과 운영 서버가 어긋나 있어 생긴 오판이다. 코드만 읽고 운영 상태를 단정하면
안 된다는 것을 다시 확인했다.
